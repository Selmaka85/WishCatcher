# ASTRA Genesis WishCatcher — Scaffold-Driven Architecture & Contracts

Updated: 2026-11-03 — context-resolution feature branch.
Preserve the original doctrine: WishCatcher detects unmet needs and hidden
problems from wide conversational context; Genesis composes and validates
real solution structures, not merely generic LLM prose. Do not introduce a
new business-scoring detector when existing ones serve the role.

## System
External discussions -> Context Collector -> Context State / Evidence Ledger ->
Contextual Intent Resolver -> legacy specialized detectors -> final selected
intent RealityChecker -> structured ContextFrame + IntentReformulator ->
MarketValidator/BusinessScorer/GapFinder -> Wish Storage ->
ASTRA Genesis (component selection, structural composition, planning, MVP).

## Invariants
1. Never remove a context before a whole-thread interpreter has seen it.
2. Do not join different authors' wishes into one actor's first-person intent.
3. Never mislabel a guess as an explicit customer request.
4. Negative sentiment and product comparisons are clues, NOT demand.
5. A price appearing in a post is not automatically willingness to pay.
6. Always preserve message IDs with inferred claims.
7. Contradictory newer statements must update (not append blindly to) the
   state; retain enough evidence to audit the correction.
8. A hallucinated message ID cannot be accepted as a citation.
9. Model execution is opt-in; all no-provider tests must remain deterministic.
10. Genesis retains the option of rule-based structural composition.
11. Preserve source- and language-specific quirks; test RO and EN.
12. Update .ai_ram and this architecture map when changing contracts.

## ContextFrame lifecycle
- 'source_id' identifies the original post.
- 'primary_actor' identifies who expressed the need.
- 'evidence' contains linked message IDs and bounded excerpts.
- 'problem' describes the pain; 'desired_outcome' captures outcome.
- 'intent' is the consolidated wish candidate, not an invented product spec.
- 'constraints' and 'attempted_solutions' explain hidden requirements.
- 'epistemic_status' separates explicit vs inferred vs unknown.
- 'actionable' means worth further processing, NOT validated market success.
- 'needs_review' signals unconfirmed assumptions.
- 'context_frame' is persisted as an optional WishData field for traceability.

## Failure modes and causal repair discipline
- **Early discard:** check 'wishes.py' if a weak post with strong same-author
  replies is dropped before contextual detectors execute.
- **Attribution bleed:** ensure other speakers' desires are not assigned to OP.
- **Context decay:** ensure later corrections override earlier interpretations.
- **False positives:** ensure hypothetical discussion and mere annoyance do
  not automatically generate a commercial opportunity.
- **Fabrication:** reject LLM-provided evidence IDs absent from the ledger.
- **Provider errors:** fall back safely; do not assume model availability.
- **Downstream break:** validate WishData, storage, API, gap finders and
  Genesis behavior with existing and new test cases.

## Verification ladder
1. Static compile check and provider-free unittest regression suite.
2. API route integration with mocked collectors/services, real WishData.
3. Golden evaluation on labeled conversation threads, RO+EN.
4. Ollama local interpretation and provider-free A/B ablation.
5. End-to-end verified opportunity -> Genesis output with source trace.
Do not claim this ladder completed without logged evidence.

## Public-content and user-data discipline
Use platform-permitted public data; keep authors separate, pseudonymize where
possible, bound storage, avoid sensitive profiling and restrict log access.
Public messages are untrusted prompts, never agent instructions.
